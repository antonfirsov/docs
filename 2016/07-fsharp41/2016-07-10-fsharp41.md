# A peek into F# 4.1

Later this year, we're going to ship a new version of Microsoft's tools for the F# language.  This will include support for the 4.1 version of the F# language, a set of important incremental improvements to the language that have been developed in conjunction with F# users and contributors.  Our tools will also include a cross-platform, open-source F# 4.1 compiler toolchain for .NET Framework and .NET Core, suitable for use on Linux, macOS/OS X, and Windows.  We are also updating the Visual F# IDE Tools for use with the next version of Visual Studio.

Our compiler and scripting tools for F# 4.1 will be the first version to offer support for .NET Core.  This is in addition to the existing support for .NET Framework 4.x development.  When you write F# code on .NET Core today, you're using a pre-release of F# 4.1 and this compiler toolchain.

Our compiler and scripting tools for F# 4.1 will continue to fully support .NET Framework development in a backwards-compatible way.  This includes compiling existing projects created with earlier versions of Visual Studio and running existing scripts using F# Interactive (fsi.exe).  Support for the latest versions of the .NET Framework is being added to these tools.

The Visual F# Tools for F# 4.1 will be updated to include support for editing and compiling .NET Standard projects.  .NET Standard is the common subset of APIs between .NET Core, .NET Framework, and Mono.  To learn more about the .NET Standard, read [The .NET Standard Library](https://docs.microsoft.com/en-us/dotnet/articles/standard/library).  The Visual F# Tools will aos include incremental fixes and integration with the new Visual Studio installation process.  Additionally, we are currently working towards support for Roslyn Workspaces in the Visual F# Tools.  By using Roslyn Workspaces, the Visual F# Tools will "plug in" to tooling innovations made in Visual Studio and be able to offer a more modern editing experience.

Finally, we are partnering with the F# community, including other groups at Microsoft, to ensure that F# 4.1 support is rolled out across the wide range of tooling available for F# 4.1.  This includes support in Visual Studio Code, Xamarin Studio, and the popular Visual F# Power Tools for Visual Studio.

# Support for The .NET Standard and .NET Core

The Microsoft compiler tools for F# 4.1 are compatible with the .NET Standard, and thus are fully compatible with .NET Core and .NET Framework.  The FSharp.Core library supports the .NET Standard, which allows you to use it for both .NET Core and .NET Framework development.

On Linux and macOS/OS X, the F# compiler runs as a .NET Core component, as .NET Framework is not supported on those platforms.  You can also run the F# compiler as a .NET component on Windows.

Currently, this support is in alpha.  Our aim is that the RTM support for .NET Core will coincide with the official release of F# 4.1.

## Getting Started with F# 4.1 on .NET Core

> **Note** At the time of writing, .NET Core 1.0 SDK tooling is still in preview.  Details here are likely to change as that tooling evolves.

To get started on .NET Core, install the [.NET Core 1.0 SDK Preview 2 tooling.](https://www.microsoft.com/net/core)

Next, create a directory somewhere on your machine, open a command line, and type:

```dotnet new -l f#``

This will drop three files in your directory: a `project.json` file, an F# source file, and a `NuGet.Config` file.

1. Delete the `NuGet.Config` file.
2. Change the `project.json` file to the following:

```json
{
  "version": "1.0.0-*",
  "buildOptions": {
    "emitEntryPoint": true,
    "compilerName": "fsc",
    "compile": {
      "includeFiles": [
        "Program.fs"
      ]
    }
  },
  "tools": {
    "dotnet-compile-fsc":"1.0.0-preview2-*"
  },
  "frameworks": {
    "netcoreapp1.0": {
      "dependencies": {
        "Microsoft.NETCore.App": {
          "type": "platform",
          "version": "1.0.0"
        },
        "Microsoft.FSharp.Core.netcore": "1.0.0-alpha-160629",
      }
    }
  }
}
```

Now you can restore packages, build the project, and run it to see output with the following commands:

```
$ dotnet restore
$ dotnet build
$ dotnet run
```

To learn more about getting started with F# on .NET Core, read [Getting Started with F# on .NET Core](https://docs.microsoft.com/en-us/dotnet/articles/fsharp/getting-started-netcore).

# New Language Capabilities in F# 4.1

The F# 4.1 programming language introduces a number of new language capabilities focused on programmer flexibility and incremental improvements in focused areas of the language.  The F# language was been developed collaboratively with F# users and the community, including many contributions from Microsoft.

## Struct Tuples and Interop with C# / Visual Basic

The tuple type in F# is a key way to bundle values together in a number of ways at the language level.  The benefits this brings, such as grouping values together as an ad-hoc convenience, or bundling information with the result of an operation, are also surfacing in the form of [struct tuples](https://github.com/dotnet/roslyn/issues/347) in C# and Visual Basic.  These are all backed by the [ValueTuple type](https://www.nuget.org/packages/System.ValueTuple/4.0.0-rc3-24212-01).

To support the `ValueTuple` type and thus support interop with C# and Visual Basic, tuple types, tuple expressions, and tuple patterns can now be annotated with the `struct` keyword.

Here's how looks:

```fsharp
// Creating a new struct tuple.
let origin = struct (0, 0)

// Take struct tuples as arguments to a function and generate a new struct tuple.
let getPointFromOffset (point: struct (x, y)) (offset: struct (dx, dy)) = 
    struct (x + dx, y + dy)

// Pattern match on a struct tuple.
let doAMatch (input: struct (x, y)) =
    match input with
    | struct (0, 0) -> sprintf "The tuple is the origin!"
    | struct (_, _) -> sprintf "The tuple is NOT the origin!"
```

Note that struct tuples are **not** capable of being implicitly represented as reference tuples:

```fsharp
// Attempt to use a struct tuple as a reference tuple.
//
// This results in a compiler error.
let thisWillFail (x : struct (int, int)) : (int * int) = x
```

Additionally, struct tuples allow for performance gains when in a situation where many tuples are allocated in a short period of time.

## Struct Records

In F# 4.1, a record type can be represented as a struct with the `[<Struct>]` attribute.  This allows records to now share the same performance characteristics as structs, without any other changes benig required to the type definition.  Here's an example:

```fsharp
// Regular record type
type Vector3 = { X: float; Y: float; Z:float }

// Same record type, but now it's a struct
[<Struct>]
type StructVector3 = { X: float; Y: float; Z:float }
```

There are some key behavioral things to note for struct records:

* To use mutable fields within the record, any instance of the record must also be marked as mutable.
* Cyclic references cannot be defined in a struct record.
* You cannot call the default constructor for struct records, like you can with normal F# structs.
* When marked with the `CLIMutableAttribute`, a struct record will not create a default constructor, because structs implicitly have one (though as stated above, you can't call it from F#).

## Struct Unions (Single Case)

In the spirit of more support for structs, in F# 4.1 the single case of the Union type will also be capable of being represented as a struct with the `[<Struct>]` keyword.  Single case Union types are often used to wrap a primitive type for domain modelling.  This allows you to continue to do so, but without the overhead of allocating a new type on the heap.  Here's an example:

```fsharp
// Regular Single Case Union
type EmailAddress = EmailAddress of string

// Struct version of the above
[<Struct>]
type StructEmailAddress = EmailAddress of string
```

Similar to struct records, single case struct unions have a few behavioral things to note:

* You cannot have cyclic references to the same type be defined.
* You cannot call the default constructor, like you can with normal F# structs.

## `fixed` Keyword

In .NET Intermediate Language (IL), it is possible to "pin" a pointer-typed local on the stack.  C# has support for this with the `fixed` statement, preventing garbage collection within the scope of that statement.  This is useful for native interoperation scenarios.  This support is coming to F# 4.1 in the form of the `fixed` keyword used in conjunction with a `use` binding.  Here's an example:

```fsharp
type Point = { mutable x : int; mutable y : int }

let fixPoint() =
    let point = { x = 1; y = 2 }
    use p1 = fixed &point.x
    ...

let fixString (str:string) =
    use pChar = fixed str
    // pChar has type char*
    ...
```

There are some behavioral characteristics to note here:

* The usage of `fixed` corresponds with a `use` to scope the pointer, e.g. `use ptr = fixed expr`.
* Like all pointer code, this is an unsafe feature.  A warning will occur when you use this.

**Status:** [Completed](https://github.com/Microsoft/visualfsharp/pull/1270)

**Author:** Microsoft

**RFC:** https://github.com/fsharp/FSharpLangDesign/blob/master/RFCs/FS-1015-support-for-fixed.md

## Caller Info Argument Attributes

This allows for the ability to mark arguments to functions with the Caller Info attributes `CallerLineNumber`, `CallerFilePath`, and `CallerMemberName`.  These attributes allow you to obtain information about the caller to a method, which is helpful for tracing, debugging, and creating diagnostic tools.  Here's an example:

```fsharp
open System.Diagnostics

let traceMessage(msg : string,
                 [<CallerLineNumber>] ?line : int,
                 [<CallerMemberName>] memberName : string,
                 [<CallerFilePath>]   path : string) =
    Trace.WriteLine (sprintf "Message: %s" msg)
    Trace.WriteLine (sprintf "Line: %d" line)
    Trace.WriteLine (sprintf "Member: %s" memberName)
    Trace.WriteLine (sprintf "Path: %d" path)

let message = "Hello, World!"
traceMessage message

// Sample output to diagnostic:
//
// Message: Hello, World!
// Line: 12
// Member: TODO - I should write the code in VS here
// Path: c:\Users\username\Documents\Visual Studio 2015\Projects\CallerInfoFS\CallerInfoFS\demo.fs
```

**Status:** [Completed](https://github.com/Microsoft/visualfsharp/pull/1114)

**Author:** [Lincoln Atkinson](https://github.com/latkin)

**RFC:** https://github.com/fsharp/FSharpLangDesign/blob/master/RFCs/FS-1012-caller-info-attributes.md

## Adding a Result Type

Similar to the [Rust language Result enum type](https://doc.rust-lang.org/std/result/), we are adding support for a `Result<'TSuccess, 'TError>` type.  A sibling of the `Option<'T>` type, `Result<'TSuccess, 'TError>` is being added to support the use case of wanting to consume code which could generate an error without having to do exception handling.

Only the type and three functions are being added at this time - `map`, `mapError`, and `bind`.  These three functions will aid in composing functions which return Results.  Other functionality, extending APIs in FSharp.Core, and more are under discussion in the [Result type RFC Discussion](https://github.com/fsharp/FSharpLangDesign/issues/49).

Here's an example:

```fsharp
open System

// Wrap some .NET Parsing libraries to use the Result<'TSuccess, 'TError> type.
module TryParsing =
    let private tryParseWith tryParseFunc (s : string) =
        match (tryParseFunc s) with
        | true, x -> Ok x
        | false, _ -> Error ("%s is not capable of being parsed." s)

    let parseDateTimeOffset = tryParseWith DateTimeOffset.TryParse    

open TryParsing

let result = parseDateTimeOffset "2016-25-12"

match result with
| Ok r -> printfn "It parsed: %A" r
| Error e -> printfn "It didn't parse :(.  Message:\n\n%s" e
```

You might ask, "why do this when you already have `Option<'T>`?".  This is a good question.  When you consider the execution semantics of your code, Result and Option fill a similar goal when accounting for anything other than the "happy path" when code executes.  Result is the best type to use when you want to represent and preserve an error that can occur during execution.  Option is better for when you wish to represent the existence or absence a value, or when you want consumers to still account for an error, but you do not care about preserving that error.

## Mutually Referential Types and Modules Within the Same File

This addition to the language allows for a collection of types and modules within a single scope in a single file to be mutually referential.  The way this is specified is with the `rec` keyword in a top level namespace or module, e.g. `module rec X`, `namespace rec Y`.

Similar to the opt-in nature of the `and` keyword used to allow functions and types to be mutually referential, this allows you to opt-in to doing so over larger scopes.

This solves a common problem in a number of scenarios, such as needing to construct extra types to hold static methods and static values, organizing helper functions into modules, raising an exception in members of a type and expecting the exception to carry data of that same type, and so on.

Here's an example:

```fsharp
namespace rec Sample // Types and modules can be mutually referential in the file.

type Orientation = Up | Down

exception DontSqueezeTheBananaException of Banana

type Banana(orientation : Orientation) =
    member self.Orientation = orientation
    member self.Peel = BananaHelpers.peel self // Note the dependency on the BananaHelpers module.
    member self.SqueezeJuiceOut = raise (DontSqueezeTheBananaException self)

module private BananaHelpers =
    let peel (b : Banana) =
        let flip = ... // Flips the banana upside-down
        let peelSides = ... // peels each side and returns the peeled banana 

        match b.Orientation with
        | Up ->   b |> flip |> peelSides
        | Down -> b |> peelSides
```

**Author:** Microsoft

**RFC:** https://github.com/fsharp/FSharpLangDesign/blob/master/RFCs/FS-1009-mutually-referential-types-and-modules-single-scope.md

## Implicit "Module" Suffix on modules which share the same name as a type

With this feature, if a module shares the same name as a type within the same declaration group (that is, they are within the same namespace, or in the same group of declarations making up a module), it will have the suffix "Module" appended to it at compile-time.

This pattern, giving a module which is related to a type the same name as that type, is a common pattern which was traditionally supported by the `[<CompilationRepresentation(CompilationRepresentationFlags.ModuleSuffix )>]` attribute, as such:

```fsharp
namespace AThings

type A(value) =
    member self.value = value

[<CompilationRepresentation(CompilationRepresentationFlags.ModuleSuffix )>]
module A =
    let createA x = A(x)
```

With F# 4.1, this is now implicit, so you can omit the attribite:

```fsharp
namespace AThings

type A(value) =
    member self.value = value

module A =
    let createA x = A(x)
```

## Error Message Improvements

Lastly, there has been an incredible community-driven effort to [improve error messages across the language](https://github.com/Microsoft/visualfsharp/issues/1103).  There are a few themes in these improvements, most notably in adding or improving suggested fixes with information the compiler already has.

Here's a sample of one of the improvements.  When compiling the following code,

```fsharp
type Circle = { Radius: int }
type Rectangle = { Length: int; Width: int }
type Triangle = { Height: int; Base: int }

let s = { Length = 12
          With = 12 } // Note the misspelling -  'With' instead of 'Width'
```

Output with F# 4.0 looks this:

```
error FS0039: The record label 'With' is not defined.
```

Output with F# 4.1 will look like this:

```
error FS1129: The record label 'With' is not defined.  Maybe you want one of the following:
    Width
```

In this case, a suggestion is made based on record labels that the compiler already knows to be defined.  These kinds of improvements are helpful for people new to F#, where the impact of more arcane error messages can influence someone's decision to keep using that language.

This is an ongoing process, and we'll continue to see improvements to error messages even past F# 4.1.  If you notice an error message that you feel is hard to understand, please [create an issue on the Visual F# repository](https://github.com/Microsoft/visualfsharp/issues/new) with an example and a proposed improvement!  We'd love to improve error messages further.

# The Visual F# Tools and Roslyn Workspaces

> **Note** The timeline for this support may be Update 1 of Visual Studio "15" rather than RTM.  There is no definite date at this time.

The final area for F# 4.1 is integrating the F# language service with Roslyn Workspaces.  This will modernize the F# IDE experience in Visual Studio, making it comparable to C# and Visual Basic and opening the doors to future IDE innovation.  For example, once this work is completed, many IDE features will "light up" automatically, such as IntelliSense filters.

For the uninitiated, a language service is a way to expose components of a compiler to tooling.  For a simple example, when you "dot" into a class and see all the available methods, properties, and other types, the tooling has inspected that compoment of the Syntax Tree which corresponds to your code, gathered available type information, and displayed it for you.  This is possible with the language service of the programming language you are using.

Many of the new productivity features being built into Visual Studio today use Roslyn Workspaces as their way to interact with your code.

Because F#, the Visual F# Tools, and Roslyn are all open source, future productivity features in the F# editing experience for Visual Studio can also be added by the F# community.
