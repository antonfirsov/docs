# F# 4.1

Later this year, we're going to ship a new version of F# that we're calling F# 4.1.  As the version number might suggest, this new release of F# is focused on many smaller improvements to the language rather than a collection of big new features.

F# 4.1 will also by the version of the language which offers full support for .NET Core.  When you write F# code on .NET Core, you're writing F# 4.1.

Lastly, F# 4.1 will also feature its language service sitting atop Roslyn Workspaces.  Although this doesn't make F# a "Roslyn Language", it allows for F# to "plug in" to the huge set of language innovations made in Visual Studio and offer a modern editing experience.

Let's dive into what's coming this year.

# New Language Capabilities

In F# 4.1 we're introducing a number of new language capabilities focused on programmer flexibility and small improvements in focused areas of the language.

## Struct Tuples and Interop with C# / Visual Basic

The tuple type in F# is a key way to bundle values together in a number of ways at the language level.  The benefits this brings, such as grouping values together as an ad-hoc convenience, or bundling information with the result of an operation, are also going to surface in the form of [struct tuples](https://github.com/dotnet/roslyn/issues/347) in C# and Visual Basic which are backed by the [ValueTuple type](https://www.nuget.org/packages/System.ValueTuple/4.0.0-rc3-24212-01).

To facilitate interop with these tuples, tuple types, expressions, and patterns can now be annotated with the `struct` keyword.

Here's how looks:

```fsharp
// Creating a new struct tuple.
let origin = struct (0, 0)

// Take struct tuples as arguments to a function and generate a new struct tuple.
let getPointFromOffset (point: struct (x, y)) (offset: struct (dx, dy)) = 
    struct (x + dx, y + dy)

// Pattern match on a struct tuple.
let doAMatch (input: struct (x, y)) =
    match input with
    | struct (0, 0) -> sprintf "The tuple is the origin!"
    | struct (_, _) -> sprintf "The uple is NOT the origin!"
```

Note that this is **not** capable of being presented as reference tuple type:

```fsharp
// Attempt to use a struct tuple as a reference tuple.
//
// This results in a compiler error.
let thisWillFail (struct (int, int)) : (int * int) = x
```

Additionally, struct tuples allow for performance gains when in a situation where many tuples are allocated in a short period of time.

## Struct Records

The Record type is now capable of being represented as a struct with the `[<Struct>]` attribute.  This allows records to now share the same performance characteristics as structs.  Here's an example:

```fsharp
// Regular record type
type Vector3 = { X: float; Y: float; Z:float }

// Same record type, but now it's a struct
[<Struct>]
type StructVector3 = { X: float; Y: float; Z:float }
```

There are some key behavioral things to note for struct records:

* To use mutable fields within the record, any instance of the record must also be marked as mutable.
* Cyclic references cannot be defined in a struct record..
* You cannot call the default ctor for struct records, like you can with normal F# structs.
* When marked with the `CLIMutableAttribute`, a struct record will not create a default ctor, because structs implicitly have one, though you can't call it from F#.

## Struct Unions (Single Case)

In the spirit of more support for structs, the single case of the Union type will also be capable of being represented as a struct with the `[<Struct>]` keyword.  Single case Union types are often used to wrap a primitive type for domina modeling.  This allows you to continue to do so, but without the overhead of allocating a new type on the heap.  Here's an example:

```fsharp
// Regular Single Case Union
type EmailAddress = EmailAddress of string

// Struct version of the above
[<Struct>]
type StructEmailAddress = EmailAddress of string
```

Similar to struct records, single case struct unions have a few behavioral things to note:

* You cannot have cyclic references to the same type be defined.
* You cannot call the default ctor, like you can with normal F# structs.

## `fixed` Keyword

In .NET IL, it is possible to "pin" a pointer-typed local on the stack.  C# has support for this with the `fixed` statement, preventing garbage collection within the scope of that statement.  This is useful for native interoperation scenarios.  This support is coming to F# 4.1 in the form of the `fixed` keyword used in conjenction with a `use` binding.  Here's an example:

```fsharp
type Point = { mutable x : int; mutable y : int }

let fixPoint() =
    let point = { x = 1; y = 2 }
    use p1 = fixed &point.x
    ...

let fixString (str:string) =
    use pChar = fixed str
    // pChar has type char*
    ...
```

There are some behavioral characteristics to note here:

* The usage of `fixed` corresponds with a `use` to scope the pointer, e.g. `use ptr = fixed expr`.
* Like all pointer code, this is an unsafe feature.  A warning will occur when you use this.

Author: [Don Syme](https://github.com/dsyme)

RFC: https://github.com/fsharp/FSharpLangDesign/blob/master/RFCs/FS-1015-support-for-fixed.md

## Underscores in Numeric Literals

We're also bringing support for placing underscores in numeric literals with F# 4.1.  This enables you to group digits into logical units to make numeric literals easier to read.  Here's an example:

```fsharp
let deadBeef = 0x_DEAD_BEEF
let deadBeefAsBytes = 0b1101_1110_1010_1101_1011_1110_1110_1111
let ssn = 123_45_6789L
```

## Caller Info Argument Attributes

This allows for the ability to mark arguments to functions with the Caller Info attributes `CallerLineNumber`, `CallerFilePath`, and `CallerMemberName`.  These attributes allow you to obtain information about the caller to a method, which is helpful for tracing, debugging, and creating diagnostic tools.  Here's an example:

```fsharp
open System.Diagnostics

let traceMessage(msg : string,
        [<CallerLineNumber>] ?line : int,
        [<CallerMemberName>] memberName : string,
        [<CallerFilePath>]   path : string) =
    Trace.WriteLine (sprintf "Message: %s" msg)
    Trace.WriteLine (sprintf "Line: %d" line)
    Trace.WriteLine (sprintf "Member: %s" memberName)
    Trace.WriteLine (sprintf "Path: %d" path)

let message = "Hello, World!"
traceMessage message

// Sample output to diagnostic:
//
// Message: Hellow, World!
// Line: 12
// Member: TODO - I should write the code in VS here
// Path: c:\Users\username\Documents\Visual Studio 2015\Projects\CallerInfoFS\CallerInfoFS\demo.fs
```

Status: [Completed](https://github.com/Microsoft/visualfsharp/pull/1114)

Author: [Lincoln Atkinson](https://github.com/latkin)

RFC: https://github.com/fsharp/FSharpLangDesign/blob/master/RFCs/FS-1012-caller-info-attributes.md

## `Result<'TSuccess, 'TFailure>` Type

Similar to the [Rust language enum type](https://doc.rust-lang.org/std/result/), we are adding support for a `Result<'TSuccess, 'TError>` type.  A sibling of the `Option<'T>` type, `Result<'TSuccess, 'TError>` is being added to support the use case of wanting to consume code which could generate an error without having to do exception handling.

The type is the only thing being added at this time.  No other additions or changes which are related to the program semantics of using a Result type are being made right now.  [The semantics of what goes into the F# Core library is still under discussion](https://github.com/fsharp/FSharpLangDesign/issues/49).

Here's an example:

```fsharp
open System

// Wrap some .NET Parsing libraries to use the Result<'TSuccess, 'TError> type.
module TryParsing =
    let private tryParseWith tryParseFunc (s : string) =
        match (tryParseFunc s) with
        | true, x -> Ok x
        | false, _ -> Error ("%s is not capable of being parsed." s)

    let parseDateTimeOffset = tryParseWith DateTimeOffset.TryParse

open TryParsing

let result = parseDateTimeOffset "2016-25-12"

match result with
| Ok r -> printfn "It parsed: %A" r
| Error e -> printfn "It didn't parse :(.  Message:\n\n%s" e
```

You might ask, "why do this when you already have `Option<'T>`?".  This is a good question.  When you consider the execution semantics of your code, Result and Option fill a similar goal when accounting for anything other than the "happy path" when code executes.  Result is the best type to use when you want to represent and preserve an error that can occur during execution.  Option is better for when you wish to represent the absense of something, or when you want consumers to still account for an error, but you do not care about preserving the error.

Status: [Addition of the Type Completed](https://github.com/Microsoft/visualfsharp/pull/964)

Author: [Oskar Gewalli](https://github.com/wallymathieu)

RFC: https://github.com/fsharp/FSharpLangDesign/blob/master/RFCs/FS-1004-result-type.md

## Mutually Referential Types and Modules Within the Same File

This addition to the language allows for a collection of types and modules within a single scope in a single file to be mutually referential.  The way this is specified is with the `rec` keyword in a top level namespace or module, e.g. `module rec X`, `namespace rec Y`.

Similar to the opt-in nature of the `and` keyword used to allow functions and types to be mutually referential, this allows you to opt-in to doing so over larger scopes.

This solves a common problem in a number of scenarios, such as needing to construct extra types to hold static methods and static values, organizing helper functions into modules, raising an exception in members of a type and expecting the exception to carry data of that same type, and so on.

Here's an example:

```fsharp
namespace rec Sample // Types and modules can be mutually referential in the file.

type Orientation = Up | Down

exception DontSqueezeTheBananaException of Banana

type Banana(orientation : Orientation) =
    member self.Orientation = orientation
    member self.Peel = BananaHelpers.peel self
    member self.SqueezeJuiceOut = raise (DontSqueezeTheBananaException self)

module private BananaHelpers =
    let peel (b : Banana) =
        let flip = ... // Flips the banana upside-down
        let peelSides = ... // peels each side and returns the peeled banana 

        match b.Orientation with
        | Up ->   b |> flip |> peelSides
        | Down -> b |> peelSides
```

Author: [Don Syme](https://github.com/dsyme)
RFC: https://github.com/fsharp/FSharpLangDesign/blob/master/RFCs/FS-1009-mutually-referential-types-and-modules-single-scope.md

## Implicit "Module" Suffix on modules which share the same name as a type

With this feature, if a module shares the same name as a type within the same declaration group (within the same namespace, or the group of declarations making up a module), it will have the suffix "Module" appended to it at compile-time.

This pattern, giving a module which is related to a type the same name as that type, is a common pattern which was traditionally supported by the `[<CompilationRepresentation(CompilationRepresentationFlags.ModuleSuffix )>]` attribute, as such:

```fsharp
namespace AThings

type A(value) =
    member self.value = value

[<CompilationRepresentation(CompilationRepresentationFlags.ModuleSuffix )>]
module A =
    let createA x = A(x)
```

With F# 4.1, this is now implicit, so you can now omit the attribite:

```fsharp
namespace AThings

type A(value) =
    member self.value = value

module A =
    let createA x = A(x)
```

## Error Message Improvements

Lastly, there has been an incredible community-driven effort to [improve error messages across the language](https://github.com/Microsoft/visualfsharp/issues/1103).  There are a few themes in these improvements, most notably adding or improving suggested fixes with information the compiler already has.

Here's a sample of one of the improvements.  When compiling the following code,

```fsharp
type Circle = { Radius: int }
type Rectangle = { Length: int; Width: int }
type Triangle = { Height: int; Base: int }

let s = { Length = 12
          With = 12 } // Note the misspelling -  'With' instead of 'Width'
```

Output with F# 4.0 looks this:

```
error FS0039: The record lable 'With' is not defined.
```

Output with F# 4.1 will look like this:

```
error FS1129: The record lable 'With' is not defined.  Maybe you want one of the following:
    Width
```

In this case, a suggestion is made based on record labels that the compiler already knows to be defined in the record type.  These kinds of improvements are helpful for people new to F#, where the impact of more arcane error messages can influence someone's decision to keep using a language.

This is an ongoing process, and we'll continue to see improvements to error messages even past F# 4.1.  If you notice an error message that you feel is hard to understand, please [create an issue on the Visual F# repository](https://github.com/Microsoft/visualfsharp/issues/new) with an example and a proposed improvement!  We'd love to improve this area further.

Issue tracking improvements: https://github.com/Microsoft/visualfsharp/issues/1103

# Support for .NET Core

F# 4.1 will also be the version of F# with full support for .NET Core.  In fact, F# 4.1 will also be entirely .NET Core-based.  The compiler and FSharp.Core library are a .NET Core console application and .NET Standard library, respectively.  This work is still in alpha, but you can expect an RTM when the tooling for .NET Core releases an RTM later this year.

## Getting Started on .NET Core

> **Note** At the time of writing, .NET Core 1.0 tooling is still in preview.  Details here are likely to change as that tooling evolves.

To get started on .NET Core, install the [.NET Core 1.0 SDK Preview 2 tooling.](https://www.microsoft.com/net/core).

Next, create a directory somewhere on your machine, open a command line, and type:

```dotnet new -l f#``

This will drop three files in your directory: a `project.json` file, an F# source file, and a `NuGet.Config` file.

1. Delete the `NuGet.Config` file.
2. Change the `project.json` file to the following:

```json
{
  "version": "1.0.0-*",
  "buildOptions": {
    "emitEntryPoint": true,
    "compilerName": "fsc",
    "compile": {
      "includeFiles": [
        "Program.fs"
      ]
    }
  },
  "tools": {
    "dotnet-compile-fsc":"1.0.0-preview2-*"
  },
  "frameworks": {
    "netcoreapp1.0": {
      "dependencies": {
        "Microsoft.NETCore.App": {
          "type": "platform",
          "version": "1.0.0"
        },
        "Microsoft.FSharp.Core.netcore": "1.0.0-alpha-160629",
      }
    }
  }
}
```

Now you can restore packages, build the project, and run it to see output with the following commands:

```
$ dotnet restore
$ dotnet build
$ dotnet run
```

To learn more about getting started with F# on .NET Core, read [Getting Started with F# on .NET Core](https://docs.microsoft.com/en-us/dotnet/articles/fsharp/getting-started-netcore).

# Integration with Roslyn Workspaces

The final defining area for F# 4.1 is integrating the F# language service with Roslyn Workspaces.  This work will provide a number of benefits, most notably in providing a modern editing experience for F# in Visual Studio.  This also opens the doors for F# to take advantage of all the Roslyn-based productivity innovations in Visual Studio.

Because F# and Roslyn are open source, productivity features in the F# editing experience for can also be added by the F# community.
